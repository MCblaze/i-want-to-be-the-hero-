## Reusable coordination method

1. Assign one narrow output per thread, with baseline, exact project, allowed paths, required evidence and a completion condition. A short specification often needs only one response. Use subagents only for useful independent work.
2. Give every thread its own sufficient context. Share measured contracts and result excerpts; do not assume Bezi threads can read each other's history.
3. Track both file ownership and editor ownership. Separate folders do not prevent one thread from replacing the active scene or interrupting another's Play Mode. Planning and isolated documentation may run together; scene switching and Play Mode have one owner.
4. Put routine defaults into the brief. For this project: SpriteRenderer + BoxCollider2D; existing greybox pixel by reference; complete hierarchy in the room prefab; scene contains its instance and preview camera; compact roughly 48-unit route; named empty markers and TextMesh labels; no new scripts, dependencies or settings for B1.
5. Use Plan when alternatives require review. Use Agent for an already specified bounded result. Review once, then provide one consolidated correction/build instruction.
6. Request changed paths and compact Passed/Failed/Not run evidence. Save detailed tests to files; use images for visual decisions. Check fresh test counts/timestamps after Editor reloads instead of starting duplicate runs.
7. Measure preparation, execution and review separately, including failed attempts, model, correction rounds and visible credits. Compare similar tasks before claiming savings.

8. Validate the saved result, not only loaded Editor objects or an agent's completion claim. Check parent/local transforms, serialized font/material references, and fresh captures after save/reopen. For repeated annotation work, include a local-offset rule in the brief and require a readable overview. A successful action batch and component inventory alone do not establish visual acceptance.

Bezi showed **fewer than 10 credits remaining** during this trial. Exact before/after consumption was unavailable; no percentage saving is claimed. No credits were bought and no subscription changed.

Node 24.14.0 is present and satisfies the documented Node22+ requirement. The bridge was not installed/cached in the checked standard locations; ACP Server activation remains unverified. Nothing was installed or enabled during discovery.

Setup would enable ACP Server in Bezi's App Settings and launch the official bridge through an ACP client. The verified package version was 0.1.3; pin and recheck a supported version at setup time. Each new ACP session creates a Bezi thread. Use the workspace/project selected in Bezi, and verify negotiated capabilities before assuming existing-thread loading or concurrent prompts. App checkpoints still require app-side review.

This can reduce UI navigation and repeated screen captures. It does not itself prove lower model usage or faster accepted work. Keep a session per task, store streamed detail locally, and surface compact completion/failure reports. [Bezi thread/context guidance](https://docs.bezi.com/fundamentals/threads).
